# Settings concurrency and autosave ownership — audit batch 5

Baseline: `main` at `62189a3c8d15822779527804d6edf45e710d606f` (PR #15). Local branch: `codex/settings-concurrency-autosave-ownership`. This batch changes settings transactions and their lifecycle only. No dependency, runtime installation, persisted schema, process-adoption, general hotkey, cache, installer, or framework migration change is included. No push, PR, merge, or publication is authorized for this batch.

## Demonstrated defects and decision

Five pre-fix behavioral cases failed: disposal returned before an explicit flush finished (the writer later released a disposed semaphore); an older superseded flush wrote after its replacement; a delayed Saved callback certified a newer unwritten draft; reading a legacy import rewrote the source; and a settings save consumed/deleted an unknown fixed `.tmp` file. The red TRX reports remain under ignored `artifacts/batch5/red`. Source inspection also confirmed instance-local file coordination and stale whole-document load/modify/save callers. Separate serialized reads and writes did not protect the transaction.

The smallest coherent boundary is an additive `ISettingsStore.SaveChangesAsync(baseline, edited, token)` returning the actual committed snapshot, plus typed settings snapshot/merge policy. It changes only fields edited relative to an owner's baseline. Disjoint fields merge against current storage. Different edits to the same field reject with a reload/reapply error; identical desired values are compatible. Provider/model, runtime preference/device, and legal version/time are coherent groups. Null baseline explicitly replaces the document; existing `SaveAsync` remains the explicit replacement API. There is no new reset feature: existing programmatic replacement uses that same policy. Future/unrecognized/corrupt documents remain protected even against replacement. A corrupt startup read may still show defaults, but subsequent transactions read strictly and refuse to destroy the recoverable input. This intentionally tightens the old corruption-overwrite behavior; recovering/resetting a corrupt file requires an explicit separate user decision outside this batch.

`SettingsSnapshot` copies the mutable process-name list at the acceptance boundary. Merge is an explicit typed catalogue rather than reflective production mutation. A behavioral field-coverage test checks every current `AppSettings` property so a future field cannot silently fall outside merge policy. The default interface implementation preserves existing injected stores and coordinates `SaveChangesAsync` calls on the same object; it cannot coordinate different injected objects or raw `SaveAsync` bypasses. Production `JsonSettingsStore` overrides at the actual normalized file-path boundary. No persisted schema revision is needed; current schema is 21, and relevant compatibility documentation is corrected.

Alternatives rejected: an instance semaphore/fixed temp merely serializes some I/O; unconditional latest whole snapshot loses disjoint edits; automatic stale same-field overwrite makes old debounce timing decide user intent; distributed locking adds an unsupported cross-process protocol. Explicit conflicts are a usability tradeoff: another panel may need reopening/reloading before reapplying a conflicting edit. A failed save keeps the draft and reports failure; it does not pretend persistence succeeded.

## Ordering, ownership, and recovery

The store holds a reference-counted lease through strict read, conflict check, normalized serialization, final schema check, and commit. Absolute/relative and case aliases of a normalized full path share that lease within this process; canceled waiters do not release another owner's gate. Completed users remove the entry. Symlinks, hard links, short-name aliases, other processes, and external editors are not synchronized. A final schema recheck detects a future schema already present then, but there remains an unsupported external check/rename race.

Every write exclusively creates its own GUID temporary file beside the destination. Failed write/flush/close/replacement preserves prior destination bytes under the exercised I/O contracts. Stream release and owned temporary deletion are independent; multiple failures retain original failure evidence. Failed deletion may leave only that operation's temporary file. Unknown temporary files are never adopted or cleaned. Cancellation is checked before waiting, after acquisition, and immediately before native replacement; it can stop a precommit write even if a stream ignored its token. A completed native replacement is a commit, not something cancellation can undo. Same-directory replacement gives ordinary visibility through the OS primitive; neither the test nor `FlushAsync` proves power-loss durability. The [.NET 8 Windows implementation](https://raw.githubusercontent.com/dotnet/runtime/v8.0.0/src/libraries/System.Private.CoreLib/src/System/IO/FileSystem.Windows.cs) delegates `File.Move` to a synchronous native move. It cannot be preempted by an asynchronous timeout or exception guard.

Autosave owns a serial chain of accepted debounce, explicit flush, writer, status dispatch, and cancellation-callback work. New requests supersede queued work, and writer admission rechecks revision/token after waits and Saving callbacks. Invalid revisions also prevent an earlier captured save from being admitted after reentrant validation failure. Caller cancellation bounds a flush wait without orphaning its accepted write. Repeated disposal shares completion, closes admission, forces the latest valid debounce, and drains the chain before token disposal. Explicit CancelPending discards queued intent; it cannot undo an admitted side effect. A save/cancellation callback must request shutdown without awaiting itself; mistaken self-await fails promptly while shared cleanup remains owned. Subscriber faults are isolated through batch 4's payload-free reporting boundary, without swallowing persistence failures. Throwing cancellation callbacks are retained as teardown faults while independent saves/cleanup continue. Cancellation executes outside state locks, and token sources remain owned until those callbacks finish.

The controller captures validation, snapshot, and revision together. It tracks cumulative accepted edit intent separately from committed state, including rapid edit/revert sequences. At writer admission, intent is rebased on the preceding owned writer's actual outcome; a canceled queued request is not assumed committed, and an uncooperative committed request is not assumed undone. Persistence bookkeeping survives UI suppression during quit. Saved notifications identify submitted and committed snapshots and owner revision. Older commits rebase later local edits, retain newer previews, and cannot certify them as persisted. Invalid drafts cancel pending queued saves; valid accepted pending edits drain on ordinary panel/window close. Inline Workbench hide keeps its live owner/debounce; reopen reflects current state. Unscheduled edits, invalid drafts, explicit cancellations, failed writes, and forced termination are not guaranteed saved.

Controller load, flush, model/audio refresh/preparation, benchmark, import, and export operations retain stable linked tokens and completion ownership. Disposal closes admission, cancels/drains accepted operations, then drains owned autosave, unsubscribes, and releases lifetime state. Ignored cancellation cannot authorize later stages or mutate a closed owner. Borrowed test coordinators remain the caller's disposal responsibility. Unresponsive work remains retained; PR #13's outer shutdown deadline reports incomplete cleanup and continues independent stages rather than disposing beneath that work. Late UI notifications are suppressed, and queued dispatcher updates read current controller state rather than a stale event payload. Application settings/runtime callbacks use the existing serialized tray-command owner and shutdown guards; presentation-only edits retain the existing no-restart policy. Session-ending/forced exit still cannot guarantee asynchronous persistence.

Import reads strictly without source migration or defaults fallback. A newer edit or cancellation before adoption rejects delayed input. Adoption is explicit whole-document replacement intent and distinct from persistence; cancellation/option-refresh failure after adoption cannot promise rollback of a possibly committed save. Export propagates its token/failures and rejects the normalized active settings destination. Filesystem identity aliases beyond supported normalized paths remain a limitation.

## Inspection scope and compatibility

Inspected production writers: App startup legal acceptance; Workbench/tray theme, font, paper-view, zoom and quick model selection; first-run acceptance; Settings controller/panel and inline Workbench/Settings window ownership; legacy HotkeySettingsWindow; settings migration and file transfer. All active-document product writers now use field-aware updates. File transfer alone uses explicit `SaveAsync` on an external export destination. `SettingsSaved` forwarding through WindowCoordinator and App reload/runtime/hotkey application, shutdown admission, startup mutex/duplicate-instance ordering, controller model/audio preparation, and the schema/normalization readers were traced. Duplicate-instance startup still exits before settings construction/I/O. No process or runtime ownership policy changes.

The legacy public HotkeySettingsWindow has no production construction call in this tree. Its transactional updates, load/edit revision checks, and closed/error guards were reviewed; its standalone async event lifetime is not newly integrated with WindowCoordinator. Activating that unused shell would require an explicit retained-window/operation owner and isolated lifecycle tests. This is not a guarantee for arbitrary external consumers of public WPF shells or custom stores. The physical first-run/tray/model reload sequence is source-traced, not end-to-end desktop validated. Histories, publishing persistence, general document import/cache behavior, native worker execution and the rest of the entire application are not re-audited here.

The compiled contract candidate must be explicitly compared before baseline promotion: additive Core settings snapshot/update members, Settings strict-read/update members, and the Settings-tests friendship are intended. Existing signatures, dependencies and project-layer permissions must remain. Schema/normalization, PR #11–15 runtime, cancellation, diagnostics and security boundaries are preserved. Rollback is a coordinated revert of this batch's store, callers, coordinator/controller, API evidence and docs; no data-format downgrade is needed. Reverting only callers restores stale-write risk and is not a complete rollback.
