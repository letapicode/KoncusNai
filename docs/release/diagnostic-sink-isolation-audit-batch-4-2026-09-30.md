# Diagnostic sink failure isolation: audit batch 4

Baseline: main `6576a191480a6830b927e3b8117dde2cc1a18214` (PR #14).
Local branch: `codex/diagnostic-sink-failure-isolation`. No push, PR, merge, or publication.

## Confirmed defects and decision

Four initial behavioral regressions failed on the baseline: a throwing Error sink left capture running instead of resetting dictation; a final Info call faulted healthy stop and prevented restart; scope Begin replaced the operation's original exception; and an unavailable log directory aborted logger construction/startup. A final injection scan found two additional structured-interface bypasses in TranscriptionService and CohereTranscriptionService; five consumer regressions failed before changing the cached interface to the wrapped field and passed afterward. File inspection also confirmed that a flush exception skipped stream release, partial writer construction lacked independent stream release, and a write that passed the disposed check could recreate a writer after disposal.

Classification: architectural reporting boundary across existing Core contracts and implementation consumers. No dependencies, persisted formats, settings, model/runtime provisioning, process ownership, cancellation admission, or shutdown budgets change.

Decision: `DiagnosticBoundary` in Core supplies resource-free plain/structured facades at consumer injection points. It preserves structured capability, properties, exceptions, optional sinks, and constructor null validation; repeated wrapping is idempotent. Original owners still dispose original sinks. Its lazy `Report` callback also encloses risky diagnostic argument preparation. Never put a product operation, resource cleanup, export, integrity verification, or security decision inside this callback. The shared boundary consolidates batch 3 terminal reporting and lifecycle fallback policy.

Alternatives: changing only the file logger leaves injected sinks unsafe; scattered catch blocks produce inconsistent privacy and exception precedence; replacing the logging stack or asynchronously abandoning one task per message enlarges scope and loses ownership. A general background queue is not justified by the demonstrated throwing-sink defects. No new dependency or logging framework is introduced.

Operational result wins over reporting failure. Recovery and independent cleanup continue, genuine teardown aggregates and retained ownership remain, cancellation remains cancellation, startup/shutdown exit-code decisions remain owned by the lifecycle, and export still returns its actual bundle result or throws. Successful logger reporting cannot certify that cleanup succeeded. Scopes set their terminal outcome before reporting; elapsed-time formatting for Complete/Cancel/Dispose is also guarded (three controlled throwing-culture regressions failed before this final correction); concurrent/repeated terminal calls share the first outcome without calling sinks under the state lock. Stages are diagnostic annotations, not synchronization of parallel product operations.

## Failure reporting and privacy

`DiagnosticBoundary.FailureCount` is an atomic, saturated process-local counter. It contains no speech, prompt, audio, history, credential, user path, exception, stack, type, or property payload. It is readable even if the injected sink, file storage, and every external destination are unavailable. No fallback invokes Trace/Debug listeners, a callback, another file, telemetry, or the failing sink. There is no recursive retry, recovery announcement, or durable record guarantee; the count is lost on process termination. This sacrifices per-failure detail when diagnostics are broken. Same-thread recursive facade dispatch and recursive file-record preparation are dropped and counted; healthy later injected-sink calls may succeed.

Default redaction and metadata-only exports are unchanged. File records support scalar metadata (null, string, Boolean, character, numeric, date/time, GUID, enum). Nested/cyclic/custom objects are rejected without evaluating arbitrary getters or dumping their contents. Concurrent dictionary enumeration/accessor failures, exception metadata/reflection failures, serialization/redaction failures, and oversized records drop the whole record and increment the counter; they do not poison a healthy writer. At most 256 properties, 1,024 characters per key, and the configured file-size limit per message/value/serialized UTF-8 record are accepted. These are record-admission bounds, not a promise to bound arbitrary caller allocation, exception accessors, or dictionary enumeration time. Correlation IDs retain their existing timeline contract; this batch does not redesign diagnostic privacy or export formats. Missing/blank direct log messages and invalid options remain programmer-contract errors; injected consumer facades isolate reporting calls even from such sinks.

## File ownership and degraded mode

Options and path/prefix configuration are validated before I/O. Environmental directory/open/initial flush failures (I/O, access denial, security exception) produce a disabled file writer rather than failing product startup. Invalid configuration and unexpected constructor contract errors still throw, after releasing any acquired resources. A write/stat/rotation/retention-enumeration fault disables that instance. Retention reads timestamps before sorting: the original comparator performed I/O, whose exception List.Sort wrapped as InvalidOperationException, misclassifying an environmental failure. A controlled regression reproduced this before the fix. Retention I/O/access-denied deletion failures are counted and do not prevent current-file writes; old archives may remain. There is no automatic per-message storage retry. Recreating the logger through its existing owner is the recovery policy.

Record snapshot/formatting occurs outside the writer lock. Owned writer I/O is serialized with disposal. Disposal detaches references before independently disposing writer and stream; `leaveOpen` gives the stream a separate owner even when writer flush/dispose fails, consistent with the pinned [.NET 8 StreamWriter implementation](https://raw.githubusercontent.com/dotnet/runtime/v8.0.0/src/libraries/System.Private.CoreLib/src/System/IO/StreamWriter.cs). Repeated disposal and late writes cannot recreate storage. Concurrent disposal waits for active I/O. Reentrant disposal from a writer callback closes admission but defers release until that write unwinds. Wrappers never dispose an active sink. Chunk backlog and CrisperWhisper skipped-warmup reporting now happen after their state locks are released.

The implementation remains synchronous. A sink, listener reached by an injected sink, formatter, accessor, filesystem/native call, or callback that never returns cannot be preempted by exception guards. A sink synchronously waiting for its own consumer's teardown can still deadlock. No asynchronous timeout promises otherwise; PR #13's stage deadlines only bound waits once synchronous execution yields. Blocking sink work remains owned and resources are not disposed beneath active writers. Any future offloading must demonstrate need and provide a bounded queue, admission closure, drain, retained ownership, and truthful timeout reporting in a separate decision.

## Inspection coverage and limits

Inspected reporting construction/injection and calls: Core coordinator recovery/reset/stop, chunk queue/completion/disposal, fault-tolerant overlay; structured file logger, metadata/classifier/redactor, scope and timeline; LocalFileDiagnostics and explicit export; App composition/startup/quit/session-ending, lifecycle cleanup/host/window registry and tray/dispatcher boundaries; runtime creation/start/stop, readiness/shared transcription, watchdog, undo/productivity/global-toggle callbacks; Settings/first-run/History; Workbench dictation/history/chat/read-aloud/import/settings; Reader preparation/export/publishing/window callbacks; insertion focus/clipboard/UIAccess and overlay; transcription registry/service, Cohere and CrisperWhisper/background warmup. Consumer field injections use the facade; static hotkey/retry helpers guard direct parameters. Method-group lifecycle reporters keep their retained-task ownership and use the common reporting boundary. No raw operational work was moved into that boundary.

This is not an exhaustive functional re-audit of every provider, worker, importer, exporter, UI presentation, developer tool, arbitrary future sink, or payload-producing caller. Persistent Python worker, LlamaCpp chat and model-download Debug callbacks are guarded; fallback messages omit raw exception/traceback payloads. Indic Parler sidecar preparation/write/Trace callbacks are guarded and disable further sidecar reporting for that service after failure, preserving synthesis results. No automatic retry or recovery claim is made. Public sidecar location/format remains unchanged. Reader media-failure argument preparation and Cohere error-detail access are guarded. Error UI wording now says diagnostics may contain details rather than promising an error was recorded. Worker transport/native execution is adjacent context, not redesigned. Tool console implementations benefit when passed into guarded library consumers; independent tool console writes are not a new product-wide guarantee. Physical storage faults, desktop/session-ending, microphone, installed model/native worker/GPU, clean-install and real export/publishing scenarios remain unexercised. The final tests use controlled streams, fake services, owned temporary state, and existing isolated lifecycle hosts. However, earlier validation executed two pre-existing unsafe paths: the production WPF rendering test constructed the default per-user file logger, and fake Indic Parler tests appended a per-user sidecar. Those runs could create/write/rotate logs and apply retention. The no-user-log-touch requirement was violated; prior contents and effects are unknown. No attempt was made to inspect, delete, reconstruct, or restore unknown user logs. The rendering test now supplies an owned temporary logger through an internal composition seam; internal fake Indic constructors now place diagnostics under their temporary output root. Public production construction/path behavior remains unchanged. No real marker, settings/history/document, installed runtime, or unrelated process modification was requested or intentionally performed; this is not a forensic proof that every user file was unchanged.

## Acceptance and follow-up

Exception isolation, original-error precedence, success/cancellation, scope/stage reporting, independent cleanup, safe bounded fallback, injected capability preservation, file admission/disposal ownership, and explicit export failure propagation are covered by behavioral regressions. Blocking synchronous behavior and physical release validation remain limitations, not certified successes. No separate deferred audit defect currently blocks this exception-isolation design. The historical user-log isolation violation means acceptance cannot be reported as completely met, even after correcting both test seams.

Next batch: settings concurrency and autosave ownership. Revalidate merged sources; use isolated settings and controlled writers to prove concurrent owners cannot lose newer accepted updates, debounce/explicit save cannot overwrite a newer snapshot, failure preserves a recoverable prior file, shutdown owns/drains the accepted save or truthfully reports it incomplete, and cancellation/future-schema/legacy migration remain correct. Define and test the actual unsaved-change policy; do not claim autosave durability under forced termination. Keep hotkey/process adoption, cache/import policy, and installation changes separate unless a specific acceptance dependency is demonstrated.

Remaining roadmap: process ownership/adoption and hotkey startup admission; import/cancellation and cache retention; installation, download/package integrity and clean Windows prerequisites; physical Windows shell/accessibility/microphone, long-recording limits, native/model/device/GPU, session-ending, signed installer/upgrade and publishing release evidence. Plan .NET migration separately with supported-framework/dependency/packaging compatibility and before/after gates. Optional experiments must measure cold/warm startup and model residency, UI dispatch latency, repeated settings/disk work, cache growth, and CPU/GPU transcription wall time and memory before changing behavior.
