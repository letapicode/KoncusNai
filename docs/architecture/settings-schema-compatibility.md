# Settings schema compatibility

Koncus Nai writes only settings schema 21. `CurrentSettingsDocument` is the serialization contract; retired product fields are not written. Schema 19 added the versioned CrisperWhisper acknowledgement, schema 20 added project-license/disclaimer acknowledgement and UTC timestamp, and schema 21 added chat paper view. Older migrations preserve applicable acknowledgements and default paper view off. Missing automatic-runtime preference/device fields default to automatic/no override without changing provider/checkpoint identity.

The oldest supported versioned upgrade input is schema 1. Schemas 1 through 20 are converted to current `AppSettings`, normalized, and rewritten as schema 21 during ordinary load. Pre-version and negative versions remain best-effort legacy inputs. Cancellation participates in migration; a failed environmental rewrite may leave the original legacy file available for a later attempt.

Versions newer than 21 are rejected with `UnsupportedSettingsSchemaException`. Ambiguous/non-numeric schema fields and non-object documents are rejected as unrecognized. Ordinary load retains its read-only defaults fallback for corrupt JSON/I/O errors, but save transactions read strictly: neither automatic edits nor explicit replacement can overwrite a corrupt, unreadable, future, or unrecognized document. Opening/closing Settings and shutdown cannot turn those fallback defaults into a destructive rewrite.

Legacy names such as JSON `activeModelId` are migration inputs only. Current runtime code uses `transcriptionProviderId` plus `transcriptionModelId`; current serialization never writes the legacy alias.

## Concurrent updates and ownership

Production stores coordinate read/check/write/migration through reference-counted in-process leases keyed by full path with ordinal case-insensitive comparison. Relative/absolute and case aliases share the lease. Hard links, junction/symlink aliases, other processes, and external editors are not coordinated; single-instance application ownership remains a separate boundary. A final schema recheck reduces external-change exposure but is not a compare-and-swap guarantee against an external editor.

`ISettingsStore.SaveChangesAsync(baseline, edited)` applies only edited fields to the current document. Independent field edits commute. If both owners changed the same field/group to different values, the transaction fails without committing: reload and reapply the intended edit. Provider/model, runtime preference/device, and legal acceptance/version timestamp are coupled groups. A null baseline or `SaveAsync` explicitly replaces the whole supported document. The interface compatibility implementation coordinates updates on one injected store object only; persistent implementations must override at their storage boundary. Direct raw SaveAsync bypasses that compatibility merge policy.

The autosave owner retains a serial chain of scheduled saves, explicit flushes, cancellation callbacks, and status delivery. New requests supersede older work before writer admission; already admitted writers may commit despite cancellation. Notifications identify the actual committed snapshot. The controller rebases newer draft edits/previews and retains cumulative edit intent, including reversions during an uncooperative earlier commit. A canceled flush wait does not abandon its accepted write. Callback self-await is rejected while teardown remains owned.

Hiding inline Settings keeps the controller/debounce alive. Ordinary panel disposal closes admission, cancels/drains accepted view/controller operations, accelerates the latest valid accepted debounce, and drains persistence. Invalid or unscheduled edits are not implicitly saved; explicit CancelPending discards queued intent, while already dispatched writes cannot be undone. An unresolved latest save or cancellation-cleanup fault makes disposal fail truthfully. Application shutdown retains its existing bounded incomplete-cleanup policy; an unresponsive writer can outlive the deadline without its resources being disposed beneath it.

Each write creates its own same-directory temporary file with CreateNew, serializes, flushes, closes, checks cancellation/schema, and commits by the existing Windows move/replace boundary. Precommit failures preserve the prior file and release/delete only owned artifacts; a failed deletion leaves an owned temporary file and is aggregated with the original failure. Unknown .tmp files are never adopted or reconstructed. These are cooperative visibility/recovery guarantees, not power-loss durability or a guarantee about every filesystem/native partial failure. The pinned [.NET 8 Windows implementation](https://raw.githubusercontent.com/dotnet/runtime/v8.0.0/src/libraries/System.Private.CoreLib/src/System/IO/FileSystem.Windows.cs) delegates MoveFile to Windows; physical storage faults and forced exit require separate release evidence.

Settings import reads strictly without rewriting its source. Valid import replaces the draft and schedules explicit whole-document replacement; import acceptance is distinct from save completion, and later option-refresh failure cannot roll back an accepted/possibly committed import. Export remains a truthful explicit write and rejects the normalized active settings destination. Cancellation propagates to transfer operations. See the [batch 5 decision and evidence](../release/settings-concurrency-audit-batch-5-2026-10-01.md).
