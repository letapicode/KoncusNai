# Notype Process Lifecycle & Fault Matrix (REL-001)

## Purpose & Scope
This document specifies the canonical lifecycle state models, ownership boundaries, fault mitigation policies, and test contracts for all child and local background processes managed or invoked by Notype. Under backlog item `REL-001` (Work Package `WP-21`), every process family maintains explicit invariants ensuring reliable recovery, deterministic resource reclamation, bounded error buffers, and complete protection of pre-existing third-party processes.

## 3. Invariance Rules & Safety Guarantees

1. **Third-Party Immunity**:
   - Pre-existing third-party processes (external Ollama daemons, system llama-server instances, user browsers, external ffmpeg jobs) are **NEVER** killed or adopted as owned by Notype.
   - For `LlamaCppChatService`, if the health check responds affirmatively before launching, `ownedServerProcess` remains `null`, guaranteeing that `DisposeAsync` will never terminate the external server.
   - For `OllamaProcessOwnership`, pre-existing process IDs are snapshotted before any launch attempt; furthermore, PID-marker checks verify process name, executable path, and start time (within 2 seconds) to prevent killing reused PIDs.
2. **Zero Orphan Guarantee**:
   - Every spawned child process is registered for termination on cancellation and disposal.
   - In `PersistentPythonWorkerClient`, `ResetProcessAsync` calls `process.Kill(entireProcessTree: true)`.
   - In `LlamaCppChatService`, any startup timeout or startup cancellation terminates `ownedServerProcess` immediately before throwing.
   - In `UiAccessHelperProcessBridge`, cancellation or timeout explicitly terminates the helper process before exiting.
   - In `ReaderVideoExporter`, cancellation immediately triggers `process.Kill(entireProcessTree: true)` via `CancellationTokenRegistration`.
3. **Stderr Flood Protection**:
   - In `PersistentPythonWorkerClient`, background standard error pumping uses a bounded buffer (maximum 64 KB).
   - If worker output floods stderr, excess characters are truncated from the head so the most recent diagnostic context is retained without risking `OutOfMemoryException`.
4. **Actionable Diagnostics Without UI Traceback Leakage**:
   - Python stack traces are written to `Debug.WriteLine` for developer diagnostics and excluded from user-facing error strings.
   - Actionable worker error messages and condensed ffmpeg errors are surfaced to provide clear remediation steps.
